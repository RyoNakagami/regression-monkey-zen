I. Code Reviewの本質

1. Code Reviewはdiscernment（見極め）の営みであって，門番役（gatekeeping）ではない．
その目的は，新たな寄与が共通コードベースに対して欠陥・ドリフト・不要な複雑性を持ち込
むことなく，既存の規約と意図を保ったまま前進させていることを確かめることにある．

2. Datascienceの文脈では，code reviewは分析そのものの妥当性をも守る営みとなる．
正確なinference, 一貫したdesign, 分析パイプラインの再利用性，数か月にわたる反復に
耐えるmaintainability, そしてチーム内での暗黙知の共有． これらすべてがcode review
の射程に入る．

3. Discernmentとは，そのコードが存在する理由を問うこと．authorの意図にも，reader
の理解にも，systemの正しさにも貢献しないものは，礼儀として黙認するのではなく，
問い直すべきである．

4. Reviewは方向転換できる最後の安価な瞬間である．一度mergeされた行は，以後のコード
が模倣するprecedentとなる．

II. Checkpoints

5. Purpose（目的）. このコードはauthorが意図したことを達成しているか？意図が不明
瞭であれば，それ自体が一つのfindingである — 実装を評価する前に，意図を明示してもらう．

6. Correctness（正しさ）. 明らかなlogic errorはないか？authorが意図した読み方では
なく，machineが実際に実行する通りにコードを読むこと．

7. Completeness（網羅性）. 要件に照らして，すべてのケースが実装されているか？
静かに落とされたbranch, 未処理のinput, 残されたTODO負債を見逃さない．

8. Conformance（規約適合）. 周辺コードベースの既存style・conventionに従っているか？
ある一ファイルに持ち込まれた新styleは，次のファイルではdriftとなる．

9. Improvability（改善余地）. 意図を損なわずに，もっと短く・速く・明瞭にできないか？
gold-platingは避け，見合うだけの価値がある変更だけを提案する．

10. Approach（手段の妥当性）. これは目的を達成する最良の方法か，それともたまたま
最初に動いた方法に過ぎないか？別ファイルの小さな変更で，このdiff自体が不要になる
場合もある．

11. Edge cases. 空入力，null, 境界値，並行アクセス，部分的失敗． authorが想定し
ていないであろう条件をコードは扱えているか？

12. Abstractions. 反復から有用な抽象が立ち上がっているか，あるいは単純なコードを
覆い隠す早すぎる抽象になっていないか？似た三行は，誤った抽象より優れている．

13. Tests. unit testsは適切か？testsはimplementationではなくcontractを検証し，
contractが変わったときに大きな声で失敗するべきである．

14. Documentation. 意図が自明でない箇所にcomment・docsがあり，コード自身が語って
いる箇所には無いか？コードを言い換えるだけのcommentはnoiseであり，隠れた制約を
捉えたcommentはgoldである．

III. Reviewerとしての規律

15. 悪い点だけでなく良い点も名指す．優れた選択を言語化することはチームにとって
「何が良いか」を教える行為であり，merge後の沈黙は何も教えない．

16. 人ではなくコードを批評する．対象はdiffであり，相手は協働者である．

17. 意図が不確かなときは断定よりも問いを選ぶ．「なぜこのapproach？」は「これは
間違っている」よりも多くのbugを浮かび上がらせる．

18. 推奨アクションのないreviewは不完全である．承認するか，変更を求めるか，
escalateするか． authorに沈黙を解釈させてはならない．
